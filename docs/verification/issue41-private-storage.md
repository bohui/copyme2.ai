# Issue 41 private Storage acceptance

This feature uses a separate private `memoir-private-photos` bucket. The API authenticates every image read as the verified owner; no public or signed download URL is returned or persisted. Storage access follows the owner metadata row, not the original path prefix, so an authorized guest transfer revokes the old guest immediately without moving bytes through public URLs.

## Deployment prerequisite (not deployed by this change)

The Supabase Storage service must provide its documented `storage.allow_any_operation(text[])` helper and set the operation context on each request. See [Storage helper functions](https://supabase.com/docs/guides/storage/schema/helper-functions) and the [official operation names](https://github.com/supabase/storage/blob/master/src/http/routes/operations.ts). Missing helpers, missing operation context and unknown operation names fail closed. Do not remove this restriction or substitute a path-prefix policy to make an older deployment work.

Allowed operations:

- Authenticated GET/info for ready photos owned by the current principal
- Upload to a pending path generated by the backend
- Delete and its required SELECT solely for logically deleted or pending objects

Signing, public reads, listing, overwriting, copying, S3 and unauthenticated access are not permitted by these policies. Logical deletion fences canonical projections first; the backend then asks Storage to delete the bytes. A failed physical cleanup leaves content inaccessible and can be retried using the same owner record.

## Repeatable database checks

Run the private-photo, PostgreSQL, primary acceptance, reuse and migration-atomicity suites with the established conventional PostgreSQL fixture. At commit `4eb78d9793e3d814d0fa814a71a7905661696774`, these 54 cases passed on PostgreSQL 18.3 with zero failures/errors/skips. The fixture creates only disposable databases; no configured Supabase endpoint or credentials are read. Operation names are a controlled service boundary in these SQL tests, not a claim of end-to-end Storage HTTP verification.

Restricted runners can opt into `MEMOIR_TEST_POSTGRES_BACKEND=single-user` for actual PostgreSQL schema, RPC and transaction behavior. PostgreSQL standalone mode has implicit superuser RLS bypass even after SET ROLE. The native RLS checks are explicitly skipped in this mode. A standalone pass is not owner-isolation acceptance, concurrency proof, or Storage HTTP acceptance.

## Remaining remote HTTP gate

The designated verification target is the remote development Supabase project. A local Storage/Auth stack is not part of the current plan. Existing target/schema/helper/principal preflight found the private bucket and feature endpoints unavailable through the exposed interface; verified TLS/database inventory and exact migration/security scope remain unresolved. PostgREST unavailability does not prove underlying database absence. Do not bypass certificate verification or replace the real operation helper with a stub.

Use only bounded synthetic images/identifiers and existing authorized least-privileged principals. Verify actual owner access and outsider/no-session denial, signed/public/list/copy/overwrite restrictions and exact-object deletion. Check response bodies and persistent outcomes: bulk signing/deletion can return HTTP200 while denying every item. A Storage DELETE response identifying the object supports API-confirmed cleanup; independent physical-byte removal requires appropriate backend evidence.

Shared-member coverage requires a verified member and a successful normal project-access control using the same identity. Guest transfer has account-wide effects and no ordinary inverse; a synthetic project namespace does not confine it. That case needs demonstrably disposable existing guest/destination principals and explicit authorization for its broader effects. Missing identities or prerequisites remain blocked rather than being replaced by mocked success.

Normal photo deletion retains metadata tombstones, namespace project state and a correction-outbox receipt. It does not provide a complete owner-scoped purge. Record run-owned residue and confirm the deployed worker's handling of a fresh zero-round namespace before writes; do not infer model-call authority from cleanup. No migration, Auth identity/credential creation, policy/security change, administrative purge or production data access is authorized by this verification document.
