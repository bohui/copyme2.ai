# Unify Lane B orchestration and map skill lanes, modes, and triggers

## Problem Statement

Memoir's skill catalog mixes foreground behavior, durable background work, asynchronous browser/research services, deprecated instructions, and integrations whose execution is not wired or enabled. A maintainer cannot infer from a skill's presence whether it actually runs, which execution surface owns it, which conversation modes permit it, or whether a round number is relevant.

The storyteller needs the conversation to stay responsive while the appropriate background work runs. Explicit profile/language choices and disabled features must prevent unnecessary or unauthorized dispatch. A map that simply assigns every packaged skill to A or B, or says all skills run at round twenty, would conceal the current implementation and create incorrect expectations.

Comfort, explore, and shape add an independent applicability dimension. Story-game must require shape plus an explicit UI button action, while the other active skills must not be restricted to a conversation mode. The UI's thinking steps must report work actually applied, including late background results, rather than implying that a listed, eligible, queued, or cached skill has just executed successfully.

Different names currently also hide different execution and recovery mechanisms: durable memory lanes, after-reply research with its own persisted claim, browser-triggered grouping, and photo-worker jobs with public-result caching. These paths need one logical background owner and truthful progress, not one serial worker or one persistence model. The requested scheduling contract has exactly two periodic skills: memoir-composer and memoir-memory-context; the other active skills require content, state-change, or explicit-action rules.

The profile-parser cleanup in [Issue 75](https://github.com/bohui/copyme2.ai/issues/75) should remain a focused work item. Shared Lane B orchestration, the cross-skill execution map, and their verification requirements belong in this separate ticket.

## Solution

Adopt two logical lanes: A owns the immediate conversation; B owns background skill orchestration. Behind B's shared admission and progress interface, reuse independent memory, composition, grouping, research, and photo runners. Unify logical ownership and policy, not worker processes, canonical writers, public caches, or every asynchronous helper.

Maintain one code-backed eligibility map for all ten catalog entries, recording the target lane, actual execution type, permitted modes, trigger type, cadence or qualifying rule, required gates, and current implementation status. Distinguish this target from today's partially separate execution paths.

Use the map as the contract for the existing dispatch/admission checks and acceptance evidence. A row indicates eligibility, not a mandatory model request. Respect manual settings, content relevance, feature flags, entitlement, cache state, and disabled/unwired integrations before dispatch. Keep proposed behavior visibly distinct from implemented behavior.

Allow the other active skills in comfort, explore, and shape without relaxing their existing gates. Permit story-game only in shape following a dedicated UI button action; neither a round milestone nor entering shape starts it. Keep its presently unavailable execution path closed. Reuse the existing progress stream, background readiness, and workspace reporting to show truthful skill names, execution types, and lifecycle outcomes without exposing private reasoning.

Treat Issue 75 as the owner of the scheduled profile-parser implementation. Reference its agreed rounds and manual-confirmation rules without implementing a second profile scheduler or copying those rules into a competing authority.

Only memoir-composer and memoir-memory-context are periodic skills: composer defaults to rounds 5, 10, 15, 20, and onward; the planned profile parser defaults to 1, 5, 10, 20, 30, and onward. All other active skills are rule- or explicit-action-triggered, even if their rules are evaluated after each accepted source. Worker polling, cache expiry, retries, and lease heartbeats are infrastructure mechanisms, not additional periodic skill schedules.

## Implementation Decisions

- **Scope:** unify background skill admission and progress under logical Lane B, reusing existing runners, and maintain the cross-skill lane/mode/trigger map. Reconcile dispatch with this policy and require truthful UI skill-progress reporting. Specify the shape-plus-button story-game admission contract without enabling its currently disabled execution or completing unwired integrations. This publication is a specification update, not runtime implementation.
- **Evidence:** inspect actual entry points, prompt/contract construction, scheduler claims, background service callers, and persistence receipts before classifying an entry as implemented. A skill file, manifest entry, legacy builder, UI label, or synthetic trace alone is insufficient evidence of invocation.
- **Role vocabulary:** in the target design A is the foreground governed collector and B is the logical background orchestration owner. The durable timeline/composer worker and independent grouping/research/photo runners are execution types behind B, not extra lanes. In the current implementation only timeline/composer are owned by the existing durable lane worker; several enrichment paths still have separate callers and lifecycle rules. Mark those as consolidation work rather than claim that naming alone has moved their execution.
- **Shared orchestration module:** use a small application-owned interface over the existing orchestration seams: accept authenticated source/change/action references, evaluate skill eligibility, dispatch the existing runner, and expose correlated progress/readable outcomes. Keep eligibility policy in one place and let runners retain their domain validation, canonical commits, and transport. A and UI actions provide bounded work references, not caller-selected permissions or raw private payloads in queue metadata. Do not create a replacement generic workflow platform, a giant multi-skill prompt, or a pass-through wrapper that leaves independent competing eligibility policies intact.
- **Independent execution and dependencies:** preserve bounded model/browser/provider capacity and reserve capacity for memory/profile persistence and composition. A slow photo search or unavailable historical provider must not occupy the canonical memory lease or block eligible memory commits. Serialize only writes sharing canonical state; enforce real dependencies such as composer consuming an extraction-complete authorized snapshot. Independent enrichment may run concurrently and fail/retry independently. No global serial queue or transaction encompasses all of B.
- **Persistence and recovery:** retain canonical personal-data writers and their source/policy fences separately from shared public-reference caches. Timeline/composer already have durable lane receipts; historical research already has a separate persisted claim; photo jobs/cursors are currently process-local with an optional persisted public-result cache; grouping is currently request-driven. Preserve these distinctions behind the shared interface. Reuse existing durable acceptance/outbox obligations where work must survive disconnect/restart; do not force cache reads, pagination, or every asynchronous helper into a durable job, or expand the timeline/composer lane table to store unrelated task types merely for naming consistency.
- **Migration ownership:** route each integrated trigger through one admission/dispatch owner, with scoped idempotency keys and existing rollout/rollback controls. Adapt or retire the replaced callback rather than leave both old and new paths enqueueing the same task. Keep existing runner-specific completion/commit validation. A unified trace must not fabricate stronger recovery or completion guarantees than the runner provides.
- **Mode applicability:** record comfort, explore, and shape independently of lane, round, and trigger. Every non-deprecated skill other than story-game is eligible in all three modes, subject to its other gates and implemented status. This does not require running every skill in every mode/round, reinstate deprecated localization, wire Family extraction, or make disabled research available. Do not confuse these conversation modes with a narrator's life stage.
- **Mode authority:** use the existing server-owned persisted conversation phase for capability admission, including its revision. The current game admission reads PhaseState; the newer InterviewStrategyPlan and A's used_strategy are separate interviewing hints/outcomes, not consent or capability authority. Do not substitute automatic internal shape for persisted phase eligibility, accept a client-supplied mode as proof, or add another LLM mode classifier. Preserve explicit pacing and existing strategy rollout/legacy compatibility; no new general mode picker is required by this ticket.
- **Trigger authority:** only memoir-composer and memoir-memory-context use periodic conversation-round schedules. Derive their due work from the server-owned completed-round ledger: composer defaults to 5, 10, 15, 20...; profile defaults to 1, 5, 10, 20, 30... under Issue 75. Existing authorized composer corrections/rework remain nonperiodic exceptions. All other active skills require source-content, relevant state-change, or explicit-action rules; none gains an every-N-round fallback. Event/place processing may recover accepted evidence without a completed reply. Evaluating a rule after each source is not an unconditional skill invocation. Poll intervals, heartbeat/TTL timers, and retries do not change a skill's trigger classification or introduce another round counter.
- **Pre-dispatch gates:** match existing application-owned eligibility checks to the map. Lane, mode, round/content trigger, required explicit action, and existing authorization/feature gates are conjunctive, not alternatives. Evaluate current scope, manual settings, no remaining profile targets, full-profile stop, content relevance, due status, feature flags, entitlement, and cache/deduplication where applicable. Record a bounded skip reason. The model cannot choose a new execution lane or enable a blocked capability.
- **Story-game action:** require a dedicated, authenticated UI button action as well as authoritative shape. An ordinary conversation message, mode transition, round milestone, profile completion, saved consent alone, or model suggestion cannot substitute for that action. A future bound dispatcher must recheck current project ownership, phase/revision, durable composition completion, adaptation consent, existing entitlement/evidence gates, and availability. Use the existing scoped action/replay conventions so a double click or retry cannot create duplicate generation. A mode change or revoked authority before admission must reject the stale request. Until execution is integrated, keep the button unavailable or explicitly explain unavailability and make no generation call.
- **Profile dependency:** Issue 75 owns the profile skill repurposing, successful profile cursor, evidence catch-up, manual field protection, full-confirmation stop, and associated localization guard. Reference that work and its status; do not duplicate its implementation or broaden its personal-data contract.
- **Actual-call accounting:** represent deterministic localization/grouping, ordinary photo-service calls, embedded extraction responsibilities, and independent model requests accurately. Several skill responsibilities may share one B model pass. Loading an instruction document is not equivalent to dispatching a standalone model call.
- **Thinking-step contract:** report actual applied skill responsibilities through the existing progress/readiness/workspace seams. Include the stable skill identity and actual execution surface; distinguish a model invocation, embedded responsibility in a shared pass, deterministic service, and cache reuse. Never synthesize a successful skill step from catalog presence, mode eligibility, a due round, prompt loading, or a model's self-report. Ordinary A reply/context/save progress remains application progress, not an invented catalog-skill invocation.
- **Thinking-step lifecycle:** distinguish queued from running, actual completion from persisted save, failure from success, and cache reuse or explicit skip from fresh work. A completed model response is not proof that its result was committed. An empty/reply-only B receipt must not claim a skill-model call. Transition only on corresponding orchestration/service/commit evidence; entering a later phase does not automatically prove every earlier phase succeeded. Preserve the current thinking-steps visibility control and locale behavior.
- **Background progress correlation:** associate steps with the current account/project and stable turn/job or covered-source interval. Attach late workspace/B updates even if their first step arrives after reply completion, without requiring a previously rendered matching step. Coalesced work must identify its actual coverage rather than claim every triggering round ran separately. Upsert/deduplicate replayed events, recover persisted/readable outcomes after reload, and ignore stale cross-project updates. A must not wait for this display to finish.
- **Public transparency only:** show bounded, localized operation labels and safe failure/skip reasons. Do not expose private chain-of-thought, strategy objectives, hidden candidate pools, prompts, raw source text, or credentials. Skill-progress visibility does not change the separate consent/privacy rules for narrator data.
- **Disabled and reserved capabilities:** retain current Family entitlement rules and the lack of canonical Family dispatch where it remains unwired. Retain the unavailable story-game admission. Their rows state intended eligibility and present gaps, not acceptance of a new implementation.
- **Flag compatibility:** the map describes the target enabled two-lane orchestration and separately labels current implementation. Preserve the current disabled-path place behavior in A and mark that compatibility exception. Reuse existing rollout controls when integrating shared admission/progress; do not enable blocked features or physically merge workers. Broader deployment or changes to operational defaults require their own reviewed implementation.
- **Single maintained reference:** keep this map as the cross-skill reference and link other implementation work to it. A lane/mode/cadence/enablement change must update both its owning implementation and this evidence-backed status. Reuse existing orchestration/admission/progress seams rather than build a generic replacement scheduler.

Source/rule-driven work does not wait for those milestones. The existing flag-off canonical path still permits its current place extraction in A. “All three” means comfort, explore, and shape, not automatic dispatch or a life-stage restriction.

Lane A's collector is application code and a system/structured prompt, not an eleventh skill from this catalog. It runs for each actual conversational response, choosing/adapting the immediate question and the small work decision. B may prepare future candidates/strategy through its existing contract; A retains immediate delivery authority. A round that reaches twenty does not automatically activate all skills, and packaged/loaded instructions do not by themselves prove a model invocation.

The periodic set is exactly {memoir-composer, memoir-memory-context}. A timeline/place rule may qualify on consecutive sources, while photo/grouping rules may qualify between conversation rounds; neither is periodic. An infrastructure retry resumes already admitted work under its original identity, not a newly due skill invocation.

### Current progress evidence and required reconciliation

The current API progress helper can emit skill-tagged operation summaries, and the browser already reports composer, place-grouping, and photo progress. This is partial implementation, not evidence that every applied skill is represented correctly. In the inspected code, composer pending work can be marked running and previous phases are marked completed when a new phase appears; workspace updates without an already matching trace can be dropped; photo cache hits use a completed status. Reconcile these behaviors with the lifecycle and correlation requirements above, using actual orchestration evidence and existing UI seams rather than a cosmetic catalog list.

## Testing Decisions

- **Existing acceptance seam:** retain the authenticated canonical conversation API and existing authorized workspace/action entry points, actual runner orchestration, provider-admission observation, progress rendering, and persisted readback already discussed. Exercise the shared B interface through these real callers; do not add a parallel test-only dispatcher. Issue 75 retains its profile implementation tests.
- **Observable behavior:** verify where a request is actually dispatched, whether a model runs, and what is committed or returned. Avoid tests that merely assert table strings, prompt names, import locations, or fabricated skill trace labels.
- **Round matrix:** cover first-source extraction, ordinary non-milestone rounds, round five, round ten, round fifteen, round twenty, and later rounds. Separate the requested profile schedule from the existing composer schedule. Label profile cases that depend on unfinished Issue 75 rather than claiming them already implemented.
- **Exactly two periodic skills:** observe actual admissions at and between the configured milestones. Prove that only composer and memory-context can be made due by a completed-round threshold, and that a round-five/twenty event with no qualifying content/action does not dispatch other skills. Conversely, eligible source/place/UI-action rules must work on non-milestone rounds or between rounds. Poll ticks, heartbeat/TTL expiry, empty/reply-only receipts, and retry attempts must not create an every-N-round schedule or falsely report a new skill call.
- **Unified ownership:** drive the existing conversation, workspace, after-reply, and UI-action callers through shared B admission/progress while observing the actual independent runner. Verify one dispatch owner, stable work identity across callbacks/replays, and no duplicate launch when old and new entry points overlap during migration. Missing integrations remain blocked.
- **Independent capacity and failure:** block/fail photo and historical runners while allowing the memory runner to commit eligible timeline/profile work and composer to process an already authorized extraction-complete snapshot. Verify A still completes independently, failures do not spread between unrelated task types, dependency waits are respected, and private memory never appears in shared public-reference cache payloads.
- **Recovery distinctions:** recover required accepted-source work after disconnect/restart with existing receipts and fences. Preserve research claim expiry/recovery, photo cache reuse and expired cursor handling, and request-driven grouping semantics through the shared interface. Do not claim that cached result persistence makes process-local photo jobs durably resumable or require all optional UI lookups to become durable jobs.
- **Mode matrix:** exercise comfort, explore, and shape at the same existing orchestration/admission seam. Other active skills must not be denied solely by mode; verify that relevance, cadence, manual stop, flags, entitlement, and integration availability still gate them independently. Deprecated localization must never regain an LLM invocation. Cover a comfort-mode source with real memory/place evidence and eligible composer work without requiring a mode transition.
- **Story-game negative/action matrix:** comfort or explore plus a button remains denied; shape without the dedicated action remains denied; mode entry, milestone, narration, model suggestion, or consent alone makes zero generation calls. Cover forged mode/action payloads, automatic internal shape with non-shape persisted phase, stale phase revision, revoked consent, unavailable integration, and repeated clicks. Even shape plus a button and otherwise valid metadata must remain unavailable while the binding is disabled. Future enablement must additionally prove one authenticated button action produces at most one admitted job under all durable gates; do not fabricate that positive capability in this ticket.
- **Manual controls:** verify protected profile fields are absent from targets, full-profile confirmation prevents profile invocation, and an explicit UI/profile language choice causes zero first-reply detector/localization calls. Reuse the corresponding Issue 75 tests and receipts instead of creating a second implementation.
- **Content and service triggers:** verify no place work from irrelevant narration, grouping after an eligible place update, photo lookup under the selected place/period and cache scope, and historical research only after eligible reply delivery with research enabled. Observe actual service requests separately from model calls.
- **UI progress acceptance:** drive the existing authenticated conversation/worker/service flows through to the rendered thinking steps. Compare visible skill identities, execution types, and statuses with observed dispatch and committed/readable results. Cover shared timeline/place extraction as one model pass, deterministic grouping, cached photos without fresh provider work, skipped profile work, queued versus running composer work, failed/retried commits, and a successful persisted save. A skipped/disabled entry must not appear applied or completed. Include locale and thinking-steps-off regressions without exposing private reasoning or plans.
- **Late/replay progress:** block B or a workspace service until after reply delivery, then release it and verify the correct turn/coverage receives a late step even without an initial matching trace. Reload/read back, replay duplicate events, coalesce several rounds, and switch projects while work is pending; no lost updates, duplicate invocations, false phase completions, or cross-project traces are allowed. These extend the existing acceptance flow, not a parallel test-only execution engine.
- **Blocked capabilities:** prove that missing Family integration/entitlement and unavailable story-game admission cannot be bypassed by a skill manifest or round number. These tests establish blocked status, not completion of the missing feature.
- **Foreground independence:** use the existing blocked/failed B barrier pattern to prove a relevant optional background task does not block A's useful reply, validated question, or durable save.
- **Compatibility:** cover enabled and disabled two-lane modes, flag-off place behavior, replay without duplicate rounds, coalesced milestones, and account/project scope. A proposed policy change cannot be reported as a current passing behavior without implementation evidence.
- **Prior art:** use existing two-lane streaming barriers, native timeline-page persistence, progressive composer cadence, operation-progress/UI trace handling, locale bridge, grouping, photo, historical research, and game admission coverage. Classify stale imports/fixtures honestly; broad repair of inherited failures is outside this mapping task.

## Out of Scope

- Reimplementing or expanding the profile-parser work in Issue 75.
- Changing the agreed profile/composer schedules, free-round allowance, or language preference semantics.
- Wiring Family-tree extraction, enabling the story game, physically merging independent runners into the durable memory worker, or forcing all work into one serial queue. Shared logical B admission/progress over existing runners is in scope.
- Building the game renderer/adaptation pipeline, introducing a general conversation-mode picker, or changing the automatic interviewing-strategy policy. The shape-plus-button admission contract and truthful progress requirements are in scope; a working game launch is not claimed.
- Creating a new general workflow/queueing platform, skill-framework replacement, or unified personal/public data store. Reuse the existing orchestration seams and persistence owners.
- Changing source/event identity, evidence authority, publication/consent, payment, or entitlement policy.
- Removing working deterministic locale/grouping behavior merely because a corresponding skill package is deprecated or not model-driven.
- Production deployment/migration, live/paid-provider campaigns, or automatic feature enablement.
