# Shared Event Index for Progressive Memoir Composition

## Problem Statement

A storyteller should be able to tell memories in any order, add details to an earlier story, correct its timing, and return later to a usable timeline and memoir draft. Today, author-timeline extraction and memoir composition maintain separate event indexes. Saved responses have one life-stage assignment, while the timeline stores events and life periods without the event-level stage/year structure needed by composer. An event discussed across several replies can consequently be represented differently in the two outputs, and an event-tag correction does not reliably reach the draft.

The current composer already supports background checkpoints every five completed conversation rounds, saved source-linked indexes, incremental evidence packets, and draft revisions. However, it selects work chiefly through response versions and chapter source references. This does not fully support several events in one reply, later replies enriching the same event, or stage/year corrections moving an event between groups. Conversation overlap can also cause unnecessary rewriting while a new detail about an older event can miss its existing chapter.

The storyteller needs one persistent account of their events, with uncertainty and original evidence retained, that drives both the timeline and progressive writing. Conversation must remain available while background processing catches up.

## Solution

Make `memoir-author-timeline` maintain the shared, source-linked MemoryEvent index in PostgreSQL through validated application services. Process every accepted narrator message in the background, including messages that produce no event update. Link each message to zero or more events and let an event collect evidence from multiple messages. Preserve stable event identities, supported life-stage/year tags, uncertainty, and explicit user corrections.

Make `memoir-composer` consume that index and its original sources. At each five-round checkpoint, wait for extraction through the selected round, freeze a snapshot, and prepare only changed stage/year/event groups in bounded parallel work. Reuse unchanged generated content exactly and assemble a readable draft using explicit event-to-section and section-to-chapter dependencies. Relevant explicit corrections may refresh affected content between checkpoints.

Manage both background skills through durable queued work with one active run per project in each skill lane. New inputs and milestones arriving during a run update one pending catch-up target rather than launch another invocation. After the active run finishes or times out, the next run takes all still-unprocessed inputs through the latest available snapshot, including the ranges attempted by a failed run. Parallel partition preparation occurs inside the active composition run.

Keep the latest eligible validated draft immediately available while newer work runs, showing which round it covers. Internal event indexing applies to every authorised narrator turn. Existing Family legacy entitlement checks continue to control premium workspace display and family-tree access. Family-tree extraction remains conditional on explicit relationship mentions and relevant corrections.

## Implementation Decisions

- **Canonical ownership:** PostgreSQL holds shared MemoryEvent records, their source links, revisions, and change sequence. Agent conversation memory is a disposable context view loaded from authorised records. Temporal history and local job stores remain execution state. Reuse the existing PostgreSQL, private worker, outbox, and checkpoint infrastructure; this feature does not require a new service or database technology.
- **Shared contract:** Define one versioned application contract for event extraction, persistence, timeline reads, and composer snapshots. Extend the existing MemoryEvent vocabulary to cover events and life periods, compatible with the existing event/period distinction. The timeline skill proposes changes; the backend validates and commits them. Composer consumes canonical events and writes derived manuscript content, recording discrepancies as review flags rather than independently changing canonical tags.
- **Identity and placement:** Each event has an opaque server-owned stable ID, project/owner scope, kind, title, revision, lifecycle status, life stage, temporal placement, uncertainty, and provenance. The seven established life stages plus `unplaced` remain the stage vocabulary. Preserve existing canonical IDs or resolve them through stable aliases during migration.
- **Date interpretation:** Store the original date expression alongside an optional supported year estimate or range and its evidence basis. Unknown years remain unknown. Approximate dates remain approximate. Capture sequence and timestamps order submissions only. Age-based placement may use explicitly established birth information while retaining uncertainty; neither elapsed time nor a stage label alone establishes an exact year. Preserve competing attributed accounts until an explicit correction decision resolves them.
- **Source relationships:** Persist many-to-many event-to-source links to exact original source versions, with relevant evidence spans and attribution when available. One accepted message may add no events, one event, or several events. An event may refer to several messages. Generated summaries, assistant questions, and earlier memoir prose remain derived material and do not become independent testimony.
- **Event reconciliation:** Retrieve relevant saved events before resolving whether current testimony adds or enriches an event. Merge only when supported identity and event continuity are clear; retain unresolved candidates where they are ambiguous. Similar titles, matching years, and shared places are insufficient by themselves. Preserve source-backed before/after relationships for chronology. Keep long periods as canonical interval records instead of generating an event for every year.
- **Logical grouping:** Use stage/year/event ID as the logical retrieval and change-processing grouping. Stable event ID is the identity key. Date ranges and unknown placement receive deterministic explicit grouping without invented precision. A placement correction invalidates the former and current grouping. Start with ordinary scoped database indexes; physical PostgreSQL partitions per event are unnecessary.
- **Correction authority:** Accept authorised stage/year corrections through chat and the existing timeline workspace, extending the edit contract where necessary. Persist actor, origin, evidence or correction statement, and expected revision. Explicit user overrides take precedence over later model estimates unless the user revises them. A stale edit returns a recoverable conflict rather than last-write-wins. Index revisions and source revisions remain independently identifiable.
- **Every-turn extraction:** Enqueue author-timeline processing for every unique accepted narrator message, using a durable intent committed with the message. Processing may start alongside conversational response generation and does not hold the conversation lease during model work. Every turn is recorded for processing, but an already active timeline run defers a new invocation and accumulates subsequent turns in its pending catch-up target. A successful empty extraction advances the processing cursor. Technical replay reuses the original input and intent; a failed or pending extraction leaves visible retryable processing state and does not acknowledge that input as processed.
- **Durable queue and run ownership:** Reuse the transactional outbox, existing queue, and Temporal workers. Persist one active run and at most one coalesced pending catch-up request per owner/project/skill lane; composer output locale remains part of its snapshot and artifact identity. Event-structure generation is serialised within the timeline lane, and composition runs are serialised within the composer lane. Record every new source/change and milestone durably even while its lane is busy. Workers claim work atomically using an expiring lease and fencing token rather than process-local flags. An arrival during a run never launches another run in that lane. Completion or timeout makes the pending catch-up request eligible without relying on a new browser request or another five-round milestone.
- **Temporal orchestration:** Extend the existing Temporal integration to coordinate each project/skill lane under a stable workflow identity. Deliver durable source-change and milestone notifications through the outbox to that lane; while work is active, notifications update its pending target rather than start competing model runs. Workflow orchestration owns waiting, activity/run deadlines, bounded retries, and recovery after worker interruption. Activities load the current authorised snapshot and call the shared application services. PostgreSQL remains authoritative for accepted inputs, canonical event revisions, successful processing cursors, and pending change targets; existing local stores can retain execution checkpoints during migration. Send opaque IDs and safe change-sequence metadata to Temporal, keeping private story text and credentials out of workflow history. Application revision/token fencing still rejects a late or obsolete activity result.
- **Acceptance and round counting:** Preserve the distinction between accepted narrator input and a completed conversation round. Persist the accepted narrator source and its sequence before optional background processing, independently of assistant delivery success. A round advances only after its unique narrator input and successful assistant reply are durably committed. Typed and transcribed voice input count once. Greetings, failed replies, source edits, transport retries, extraction jobs, and composer jobs do not add rounds. A durably accepted input whose assistant reply failed remains available to event extraction and later authorised composition; it does not become an extra completed round or duplicate testimony when delivery is retried. Keep the account free allowance and project checkpoint cadence independent, retaining their current default values of twenty and five respectively.
- **Entitlements and family tree:** Internal event indexing runs for every authorised narrator turn independently of the Family legacy package. Existing premium timeline display, family-tree read/write access, and server-owned entitlement verification remain intact. This updates the earlier coupling between internal timeline extraction and premium display without changing package pricing. Dispatch family-tree extraction only for explicit relationship mentions, person details tied to an established relationship, and relevant corrections; events without such information do not trigger it. Resolve person links through canonical saved identities and preserve unresolved links when identity is unclear.
- **Extraction completion:** Persist per-turn processing status and a project processing cursor covering all applicable accepted turns through a chosen completed-round boundary. A five-round checkpoint waits until its required extraction intents have committed or completed with an empty result. A later extraction finishing ahead of an earlier one cannot imply that the gap was processed. Include the event change sequence in the frozen composer snapshot.
- **Five-round dispatch:** Retain the durable project round ledger and checkpoint milestones at five, ten, fifteen, and subsequent configured intervals. A milestone creates or updates the pending composition target idempotently; it is an opportunity to process work rather than a requirement for a separate invocation. While a run is active, later milestones wait in the same coalesced request and retain their history. When the worker claims the next request, resolve current authorised inputs and the latest extraction-complete event snapshot rather than using only the source packet captured when an earlier milestone was enqueued. Include all eligible unprocessed inputs available at that boundary, including additional turns beyond the milestone that first made the request due. If no relevant partition fingerprint changed, record completion without another drafting call. The initial private draft uses the existing private checkpoint gate; later runs use progressive updates and the saved manuscript revision. Formal-book composition remains explicitly authorised.
- **Catch-up cursors and failed ranges:** Keep separate cursors for successfully persisted event extraction and successfully committed composition, alongside the independent completed-round counter. Track original input and canonical event change sequences so edits to earlier sources also remain pending. Claiming, attempting, dispatching, or timing out a job never advances its successful cursor. The next run covers changes after the last successful cursor through its newly frozen target and includes any uncommitted range from failed or timed-out attempts. If output is saved through round five and the run for six through ten fails, a later run claimed at round twenty covers six through twenty, subject to extraction and access checks. Successful idempotent extraction results and partition checkpoints may be reused; failed work is included without replaying already committed effects or double-counting testimony. Keep processed milestone history separate from the actual covered-through input/round values.
- **Timeout and deferred recovery:** Apply a configured maximum run duration in addition to lease renewal or heartbeat expiry. A hung worker cannot renew forever. On timeout, cancel its work where possible, fence its ownership token, retain unacknowledged input/change ranges, and make the latest pending target eligible under the existing bounded retry/backoff policy. A stale worker that later returns cannot commit with its expired token. When an attempt fails before timeout, preserve its pending range for retry or a newer catch-up snapshot. A terminal provider failure remains an explicit recoverable state rather than spinning indefinitely; newer queued work and operator/user retry retain all unfinished evidence.
- **Change detection:** Determine dirty partitions from canonical event revisions, placement changes, original source versions, additions/removals of source links, explicit correction decisions, and applicable current input dependencies. Do not use a five-round cursor as the only change detector. Conversation overlap helps interpretation but is not new evidence and does not itself mark a partition dirty. An older event receiving new evidence must invalidate its generated content even when no old response text changed.
- **Immediate invalidation:** Source deletion, access withdrawal, and explicit accepted corrections mark affected outputs stale immediately. Corrections may enqueue an affected-content refresh between normal milestones without incrementing round usage. Recompute a changed event from surviving authorised original evidence; remove unsupported content rather than replacing it with invented material. Existing retention/deletion rules govern restricted source and checkpoint bytes.
- **Dependencies and content reuse:** Persist event-to-generated-section and section-to-chapter dependencies plus immutable section revisions and input fingerprints. Reuse unchanged generated context and prose directly from storage, preserving their bytes and revisions. The application enforces that a candidate cannot replace an unchanged section merely because the model rewrote it. A changed event invalidates all declared dependent outputs, including affected headings or transitions; unrelated sections remain unchanged.
- **Chapter assembly:** Partitions are evidence and update units, not mandatory chapter boundaries. Maintain stable chapter IDs, coherent chronological grouping, and a small authorised continuity context. Assembly may change display order without rewriting unchanged prose. Regenerate a transition only when its declared dependencies changed. Preserve human-edited, approved, or locked content and save proposed replacements against the exact base revision. Keep the existing chapter word-limit and evidence-review checks.
- **Parallel preparation and recovery:** Freeze the input snapshot before preparing independent dirty partition contexts in bounded parallel tasks inside the one active composition run. Checkpoint successful tasks by event/source fingerprint, locale, applicable policy/configuration versions, skill/model version, and base output revision. Resume successful work after retry. Dependencies and shared event reconciliation remain coordinated before fan-out. Serialise final manuscript commits per project/output locale with revision and run-token fencing; the storyteller remains free to submit more turns during generation. A newer milestone changes the pending target and does not start a competing set of partition tasks.
- **Late output and concurrent input:** Recheck relevant event/source versions, manuscript revision, and access policy before accepting output. New unrelated turns may leave an older snapshot eligible, with its actual coverage label retained. Corrections, deleted dependencies, or revoked access refuse incompatible late output. Reconcile against current authorised state and queue the affected work again; never let an older extraction restore a newer user override.
- **Read and edit interfaces:** Expose canonical event IDs/revisions and structured stage/date provenance through authorised event read/edit responses. Keep timeline presentation adapters independent of storage and preserve uncertainty labels. Composer snapshot reads include event/source manifests and the selected change cursor. Saved-draft reads expose the last completed milestone, extraction/composition progress, and recoverable error state without leaking control markers, credentials, or private provider diagnostics.
- **Saved-draft behavior:** Return the latest validated eligible private draft immediately. Show the covered round and a compact updating state when newer work is pending. Hide or disable reuse of outputs made ineligible by deletion or access changes. Partial extraction and unreviewed composition candidates remain pending rather than ready. This feature promises progressive saved availability, with normal lag of up to the checkpoint interval plus processing time.
- **Migration and compatibility:** Reconcile the current Family timeline document and composer indexes into shared MemoryEvent records. Retain original testimony, dates, canonical person links, privacy/print flags, and manuscript references. Preserve explicit prior identity mappings; ambiguous cross-index matches remain unresolved rather than merged by title. Import legacy records with honest provenance status when evidence cannot be recovered. Migrate existing source manifests into event links, backfill supported placement once, and stop maintaining the duplicate composer event index after cutover. Existing job checkpoints may continue as derived caches with schema-aware invalidation.
- **Account continuity:** Extend the existing authorised guest-to-account transfer mapping to event IDs, source links, processing cursors, and manuscript dependencies. Replaying a transfer preserves identity and does not manufacture new rounds, extraction intents, or checkpoint milestones. All event/source references must remain within the authorised owner/project scope.
- **Skill instructions:** Update both skill contracts and their runtime references to name the shared event service, supported tag provenance, many-to-many source links, revision rules, extraction cursor, dirty partition manifests, and unchanged-content behavior. Remove redundant composer event extraction. Align examples with the separate five-round private checkpoint and twenty-round free allowance. Keep family-tree instructions and dispatch limited to their relationship-driven role.
- **Delivery sequence:** Introduce shared persistence and source links first, adapt author-timeline writes and timeline reads, then make composer consume that index. Add partition-level invalidation and parallel context preparation over the retained queue/checkpoint infrastructure. Migrations and runtime rollout follow the existing authorised deployment process; writing this spec does not deploy the feature.

## Testing Decisions

- The primary acceptance seam is the existing authenticated story workflow: submit narrator turns, drive the background worker to an observable state, edit/read canonical events, and read the saved private draft. Prefer this seam over isolated tests of prompts, private helpers, table layout, or function-call order. Use controlled responses only at the external model/provider boundary; exercise application validation, persistence, dispatch, revision handling, and rendering together.
- A good test asserts what the storyteller or authorised caller can observe: event identity and tags, evidence links, accurate coverage, unchanged output content/revisions, corrected output, access denial, or a recoverable processing state. Tests remain valid when internal batching, queue adapters, or module arrangement change.
- Cover one reply describing several events in different stages/years and several replies describing one event. Read timeline and draft dependencies to prove both use the same canonical event ID, including a late new detail about a much older event.
- Cover explicit, approximate, age-based, ranged, conflicting, and unknown dates; unknown stage; undated events; and periods spanning years. Check uncertainty and original expressions rather than expecting fabricated numeric dates. Exercise both supported conversation languages and transcribed voice using the same persistence contract.
- Cover stage/year edits without source-text changes. Assert stable event ID, a changed revision, invalidation of former/current grouping, updated timeline and affected draft, and preservation of unrelated output. Delay an earlier extraction response and prove that it cannot restore a tag the user corrected later.
- Cover successful empty extraction, failed extraction, out-of-order completion, disconnect, restart, and replay. A milestone must remain pending while a required extraction gap exists, then compose against a snapshot covering the stated round once the gap settles.
- Cover checkpoints before five rounds, at five and ten rounds, and under a non-default cadence. Duplicate inputs, failed replies, source edits, and background jobs must not increase completed-round usage. An unchanged checkpoint advances processing state without new generated output or duplicate provider work.
- Hold a background run active while milestones at ten, fifteen, and twenty arrive. Assert that the lane still has one active invocation, then finish it and verify one catch-up run consumes the latest eligible range rather than three obsolete milestone packets. Include extra inputs arriving between milestones and prove that the worker resolves its snapshot at claim time. Perform this through the existing worker boundary for both skill lanes.
- Fail or time out an attempt covering six through ten after saving through five, then provide inputs through twenty. Assert that the next eligible run covers six through twenty, including the failed range, and that no claim or failed attempt advances a successful cursor. Reuse applicable successful checkpoints and verify that sources and already committed events are not duplicated.
- Advance a controlled clock past the configured run deadline while the original worker remains stalled. Verify that ownership is fenced, pending work becomes eligible without another user turn, and a late completion cannot save over the replacement run. Cover lease expiry after a process crash as the equivalent recovery boundary; test durable outcomes rather than sleep durations or scheduler internals.
- Persist an accepted narrator input and fail assistant delivery. Read back its source/event evidence, prove it is included in later authorised catch-up processing, and verify that completed-round usage remains unchanged. Retry the same client input and assert that source identity and evidence links are reused.
- Cover conversation overlap that refers only to unchanged material. It must not trigger rewriting. Cover new evidence for an existing older event outside the overlap window and assert that its dependent section updates. These are regressions for the dirty-content selection gaps reproduced during the review.
- Cover edits, source-link removal, deletion, and access withdrawal. Rebuild from surviving evidence and refuse late output that depends on removed or inaccessible sources. Verify that a permitted previous draft remains available during an ordinary update while an ineligible one is withheld.
- Cover independent dirty partitions with controlled delayed responses. Demonstrate bounded concurrent preparation and continuing chat, then fail one task and prove that already successful tasks are reused on retry. Verify that concurrent runs cannot overwrite a newer manuscript revision.
- Cover exact unchanged-content preservation, coherent chapter assembly, the existing word ceiling, failed evidence review, and protected text. Unchanged sections retain content and revisions; a protected affected chapter receives a proposal rather than silent replacement. A failed candidate never becomes the ready draft.
- Add focused real-PostgreSQL integration checks for the shared event service and migration boundary: user/project isolation, expected-revision conflicts, atomic change/outbox recording, many-to-many references, migration replay, and preservation of legacy IDs, provenance, and privacy. Extend the existing disposable PostgreSQL migration harness rather than adding a production test endpoint or new storage subsystem.
- Use the existing browser workspace seam for the small presentation contract: event tag editing, reload persistence, saved-draft coverage/updating status, and premium timeline/family-tree visibility. Do not duplicate every worker recovery scenario in browser tests.
- Family-tree acceptance scenarios cover a relationship mention, a relevant correction, and unrelated narration. Preserve server-owned entitlement checks and prove that internal event indexing for a non-Family storyteller does not grant premium tree/timeline display access.
- Migration and account-transfer scenarios preserve shared identity and manuscript references, retain unresolved legacy matches, and replay without extra rounds or milestones. Cross-project references and unauthorised event edits are rejected.
- Prior art includes the existing authenticated agent-turn and family-context tests, private-draft milestone/recovery tests, outbox broker tests, preview persistence/review tests, response-stage tests, disposable PostgreSQL timeline migration tests, and workspace browser tests. Reuse their public boundaries and fixtures; add new seams only where the required behavior cannot be observed through them.

## Out of Scope

- Changing package prices, payment flows, free allowance policy, premium family-tree access, or premium timeline-display entitlement.
- Automatic formal-book authorisation, publication, print ordering, or replacing existing edition/print approval steps.
- A general rewrite of the agent-memory system, a new graph/vector database, a separate microservice, or physical database partitioning per event.
- Moving every execution checkpoint and generated artifact into PostgreSQL as a prerequisite for unifying canonical events.
- Full manuscript editing, proposal approval/rollback interface redesign, or genealogy-renderer replacement beyond the event tag edit and saved-status behavior required here.
- New external history, genealogy, photo-research, media-rights management, or glossary authoring workflows. Existing dependency changes remain subject to current validation.
- Automatically filling unsupported dates, resolving ambiguous identities, merging legacy records by similar wording, or treating generated text as personal testimony.
- Guaranteeing an entirely current memoir after every reply. Timeline extraction runs per accepted message; ordinary writing checkpoints occur every five completed rounds and require processing time.
- Increasing the current source collection limits or creating a large-book chapter-task engine beyond bounded preparation and incremental assembly of the supported private draft.

## Further Notes

This is an implementation specification synthesised from the conversation and current code review; it does not claim the shared event model has been implemented. The existing product architecture already establishes PostgreSQL as canonical, original evidence and revisions as persistent state, and outbox-driven workers as the long-work boundary. The current Family document and private draft store provide migration and execution precedents.

The review ran seventy-eight focused local tests successfully. Additional controlled probes showed that timeline validation currently drops proposed stage/year fields, and that new evidence for an older event can leave its chapter marked unchanged while overlap marks unrelated content dirty. Those probes identify required regression scenarios; the passing current suite does not establish the new guarantees in this spec. Live provider behavior and deployment were not verified by that review.

The requested user-visible behavior takes precedence over the earlier rule coupling both Family skills to premium extraction: internal event indexing now applies to every authorised narrator turn, while premium display and family-tree access retain their existing gates. Preserve the distinction between accepted input, completed round, extracted-through input, and composed-through event changes/rounds in both storage and visible status. Failed background processing retains its input range. Durably accepted narrator evidence also survives an assistant-delivery failure while the completed-round counter remains unchanged.

The authenticated story workflow is the agreed primary acceptance seam, supported by focused PostgreSQL persistence/migration checks and a small browser workspace contract. This specification task does not implement or deploy application changes.
