# Langfuse evaluation research

Reviewed official Langfuse documentation on 2026-09-28. This is an architecture recommendation, not an implemented integration.

## Verified capabilities

- **Local experiments can execute the real application.** The Python and JS/TS experiment runners accept an application task function, local or hosted datasets, configurable concurrency, and item/run evaluators. SDK evaluator functions run in the experiment process. A local developer script can therefore invoke the application's worker and send results to Langfuse; a dedicated evaluation service is not required by Langfuse. Local dataset inputs are still exported to the configured Langfuse instance. [Experiments via SDK](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk)
- **UI prompt experiments are a different path.** They run a selected prompt/model over a dataset. Use the SDK task callback for an application with its own runtime, tools, persistence, and skill loader. [Experiments via UI](https://langfuse.com/docs/evaluation/experiments/experiments-via-ui)
- **A trace in the viewer is not automatically a judge's context.** Managed observation evaluators see the selected observation's input, output, metadata, and tool calls; they do not retrieve children or siblings. Put the required trajectory on the root observation or assemble it externally. Observation evaluators are recommended; legacy trace evaluators are deprecated. Managed judges execute asynchronously in Langfuse workers, outside the application. Consequently, keep timeouts, cancellation, iteration limits, and permissions in the agent runtime. [LLM-as-a-Judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)
- **Trajectory scoring needs explicit instrumentation.** Langfuse's agent cookbook records tool-call history into observation metadata. Its example records names and arguments; evaluating recovery or evidence use additionally requires capturing results and errors in this application's instrumentation. [Agent evaluation cookbook](https://langfuse.com/guides/cookbook/example_pydantic_ai_mcp_agent_evaluation)
- **External scoring is supported.** Fetch observations, assemble evaluation input, run custom checks/judges, and upload scores. [External evaluation pipeline](https://langfuse.com/guides/cookbook/example_external_evaluation_pipelines) Scores can target a trace or an individual observation through its ID; score IDs can provide idempotency when retrying writes. [Scores via API/SDK](https://langfuse.com/docs/evaluation/evaluation-methods/scores-via-sdk)

## Proposed application boundary

Use a local CLI evaluation runner → the normal application/`codex-worker` execution path → Langfuse traces, scores, and experiment comparisons. Langfuse replaces custom evaluation storage, comparison, and judging infrastructure; it does not replace Codex execution. Repository checks now run as ordinary local/CI commands, while `codex-worker` remains the only Codex execution service.

Repository inspection found `install_skill` previously targeted a separate harness's `/codex-home/skills`, whereas the worker image copies skills to `/app/skills`. The application reads selected `SKILL.md` files into module-level constants and injects them into its system prompt. Each Codex user has a separate `HOME`/`CODEX_HOME`; copying skills into the worker's root Codex home is therefore not a sufficient installation contract. The worker filesystem is read-only. The updated command validates the skill bundles, rebuilds the API and worker images, and recreates those services so cached loaders reload. A future native Codex skill-discovery implementation would need its own explicit installation contract.

The worker's current turn collector does not preserve a complete tool trajectory; `build_loop_trace` generates UI summaries rather than observed Codex event history. Capture ordered tool calls, arguments, results/errors, application actions and state commits, visible instructions/tool definitions, final response, and termination status. Associate each run with the application revision, skill content hash, model/provider configuration, and dataset case. Use deterministic checks for tool permissions, schema validity, retry/step budgets, and expected persisted state; use calibrated judges for evidence use, tool appropriateness, recovery, and final-answer quality. Judge each action using only information available before that action. These are proposed application rubrics, not built-in Langfuse guarantees.

Start with isolated synthetic fixtures and the same worker path used by the app. Preserve full-fidelity local evidence as needed, while deliberately selecting/redacting what goes to Langfuse. Recording visible events does not imply access to the model's private reasoning.
