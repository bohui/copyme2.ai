# Preserve original voice input alongside its transcript

## Problem Statement

When a storyteller answers Mira by voice, Memoir currently transcribes the recording and saves the resulting words in the canonical conversation. The connected transcription endpoint does not persist the submitted audio or return a durable recording reference. The storyteller's original voice can therefore disappear after processing, even though the conversation text survives.

This loses the storyteller's delivery, pronunciation, pauses and emotion. A transcript, an encrypted recording on one device, and Mira's generated spoken reply are not substitutes for the original recording stored in the backend.

The requirement is to preserve each original recording submitted through Memoir's voice input, alongside its transcript, and durably associate the recording with the accepted narrator source. This applies to browser voice mode, browser dictation and the native recording flow.

## Solution

Save the exact recording received from the client in private backend object storage before reporting that it has been preserved. Return an owned recording reference with the transcription result, carry that reference through transcript review and submission, and attach it to the canonical narrator source when the turn is accepted.

Keep the existing conversation and text evidence pipeline. Original audio remains available through an authenticated backend retrieval operation after a refresh, reconnect or API restart. Editing the transcript does not overwrite the recording. Typed input continues to work without audio, and existing text-only history remains readable.

Clearly distinguish a recording saved on the device, an original saved in the backend, a completed transcription, an accepted narrator source and a saved conversation reply. A failure at one stage must not falsely acknowledge another stage or require the storyteller to record again when the backend already has the original.

## User Stories

1. As a storyteller, I want my original voice recording stored with my transcribed answer, so that my memoir preserves how I told the story.
2. As a storyteller using browser voice mode, I want each submitted voice turn retained, so that automatic transcription does not discard my voice.
3. As a storyteller using browser dictation, I want the recording retained when I review and send its words, so that dictation preserves the original as well as the text.
4. As a storyteller using the native app, I want my submitted recording uploaded to the shared backend, so that its only copy is not on my phone.
5. As a storyteller, I want the exact uploaded recording preserved, so that conversion for transcription does not replace the original.
6. As a storyteller, I want each recording linked to the correct answer, so that one memory cannot accidentally receive another memory's voice.
7. As a storyteller, I want several dictation clips used in one answer retained in their original order, so that appending speech does not lose earlier clips.
8. As a storyteller, I want corrections to names and dates to keep the original recording attached, so that improving the transcript does not erase my voice.
9. As a storyteller, I want original transcription text distinguishable from my edited submission, so that the record does not imply that added words were spoken.
10. As a storyteller, I want to add typed words to a dictated answer, so that I can clarify my story without losing the recording's provenance.
11. As a storyteller, I want my recording to survive a transcription failure after upload, so that I can retry processing without repeating the story.
12. As a storyteller, I want an empty or unsuccessful transcript to leave my saved recording recoverable, so that a recognition problem does not destroy valid audio.
13. As a storyteller, I want a storage failure explained before the app claims my voice is saved, so that I know whether another upload attempt is necessary.
14. As a storyteller, I want a failed Mira reply to leave an accepted answer and its recording intact, so that an interviewer failure does not erase my contribution.
15. As a storyteller, I want retries to reuse the same recording and answer, so that a poor connection does not create duplicates.
16. As a storyteller, I want my saved recording references restored when I reopen the conversation, so that preservation does not depend on temporary page state.
17. As a storyteller, I want a clear distinction between a local recording and a backend copy, so that I understand what survives losing or changing devices.
18. As a storyteller, I want stopping, discarding and retaking to have clear effects, so that unwanted recordings are not submitted as memoir evidence.
19. As a storyteller, I want recordings already uploaded for review to remain private until I submit them, so that transcription alone does not add an answer to my memoir.
20. As a storyteller, I want discarded uploaded drafts to become inaccessible, so that a retake does not leave an unwanted recording available.
21. As a storyteller, I want my recordings preserved during supported identity linking or guest transfer, so that beginning before sign-in does not break their connection to my story.
22. As a storyteller, I want my recordings accessible only under the applicable source permissions and consent, so that private memories stay private.
23. As a storyteller, I want account switching to isolate pending recordings and responses, so that my voice cannot be attached to someone else's answer.
24. As a storyteller, I want withdrawn sources and deleted audio to stop being retrievable, so that backend storage respects my later choices.
25. As a storyteller, I want typed answers and older transcripts without audio to remain usable, so that this change does not block existing memories.
26. As a storyteller, I want unavailable historical audio represented honestly, so that generated speech is never presented as my original voice.
27. As a storyteller, I want English, Chinese and mixed-language recordings retained without alteration, so that storage does not depend on transcription language.
28. As a storyteller, I want unsupported, damaged or oversized uploads rejected clearly, so that a failed upload is not mistaken for a preserved recording.
29. As a storyteller, I want recording and processing notices to explain backend retention, so that microphone permission is not mistaken for consent to every later use.
30. As an operator, I want recording identity, verified media metadata and content checksums persisted, so that preservation can be checked independently of transcript text.
31. As an operator, I want incomplete storage writes and cleanup failures distinguishable from success, so that recoverable failures can be repaired safely.
32. As an operator, I want speech and storage diagnostics without audio payloads or private transcript text, so that monitoring does not create another copy of personal memories.
33. As a maintainer, I want recording references to use the existing canonical source and turn identities, so that audio does not create a second conversation ledger.
34. As a reviewer, I want to retrieve the same original bytes through the authenticated API after reloading state, so that acceptance proves durable preservation rather than successful transcription alone.

## Implementation Decisions

- **Authoritative flow:** extend the existing authenticated story transcription operation and canonical agent turn acceptance. Use the Supabase user-data and private Storage boundary already shared by web and native clients. Do not implement this only in the older in-memory upload/session routes or reintroduce the retired direct WebRTC conversation path.
- **Meaning of original:** retain the complete, exact byte sequence produced by the client recorder and received by the backend, with its actual container and codec. This does not promise uncompressed microphone samples that the client never captured. Transcription normalization or future playback derivatives must be separate objects and must never overwrite the original. Mira's synthesized reply is a different asset.
- **Recording persistence:** add a narrowly scoped Recording record and source-recording association. Persist opaque recording ID, verified owner, resolved conversation/project identity when available, backend-generated object location, media type, codec when detectable, byte size, decoded duration, server-computed SHA-256, creation time, upload idempotency identity, storage status and transcription status. Persist the initial ASR text and provider/model/language metadata separately from the storyteller's edited canonical text. Keep binary audio in private object storage rather than database JSON, profile state, process memory or an API container's temporary filesystem.
- **Durable upload boundary:** reserve a pending recording identity, validate and upload the complete original, verify finalization, then mark it ready. Only ready originals may be acknowledged as backend-saved or sent for transcription. Object existence alone is insufficient proof of a trusted successful upload. Partial writes remain pending or failed and are never returned as usable recordings. Database/object-store failure recovery must be retryable without exposing incomplete bytes.
- **Bounded media validation:** validate decoded base64, supported container/actual media type, non-empty content, checksum, byte size and decoded duration before external processing. Apply finite server limits consistent with the existing speech and product limits; the product's five-minute turn ceiling is an upper bound, not a reason to increase narrower native capture limits. Enforce the encoded request bound before allocating an unbounded buffer. Reject rather than truncate. Arbitrary recorder fragments must not be treated as complete independent recordings.
- **Transcription contract:** extend `POST /api/v1/memoir/story/transcriptions` with an optional upload idempotency key and optional owned project context. Existing audio payload fields remain supported. On success, preserve the existing text and transcription metadata fields and add a recording descriptor containing its ID, verified media metadata and backend-saved state. Persist a successful ASR result so retries can reuse it. A retry may identify an existing owned ready recording instead of resending its bytes; reject requests that ambiguously supply both a new payload and an existing recording reference.
- **Failure contract:** if storage fails, return a retryable preservation error and do not acknowledge a saved recording or dispatch STT. If STT fails after storage succeeds, return a safe error with the durable recording ID and separate saved-audio/failed-transcription status. Empty ASR text follows the same recovery rule and does not accept a narrator source. An authenticated metadata read must make uncertain outcomes recoverable. Do not promise exactly-once provider billing after an ambiguous upstream response.
- **Private recording operations:** provide authenticated recording metadata, exact-original content retrieval and explicit discard/deletion operations under the canonical Memoir API namespace. Responses expose opaque identities and API references, never public Storage URLs, reusable signed URLs or internal object paths. Content reads use private, non-shared caching rules and preserve the verified original media type. Draft metadata is owner-scoped; attached content reads also check current source/project policy.
- **Canonical turn contract:** extend turn submission with an optional ordered `recording_ids` collection. Resolve the authoritative conversation identity using the existing backend mapping, including the first answer when the client does not yet have a project ID. Validate ownership, ready state, policy, duplicate references and project scope before accepting any source. Atomically attach the ordered recordings to the accepted source ID/version and client turn ID in the existing acceptance transaction, covering both current conversation execution modes. Do not attach a recording to an unrelated second source or resolve scope from a client-supplied storage path.
- **Acknowledgement and recovery:** a source-accepted receipt for a voice submission with recording references must imply both durable originals and committed associations. Extend source detail, turn receipts and conversation-history projections with bounded ordered recording descriptors, without embedding audio payloads. Reloading or retrying reads these persisted associations. Preserve the existing distinction between source accepted and conversation saved; a downstream generation or workspace failure must not remove accepted audio.
- **Retry identity:** upgraded clients create a stable upload key for each captured clip and reuse it after uncertain responses. Enforce owner-scoped uniqueness; the same key and same validated payload returns the same recording, while changed bytes or conflicting immutable metadata returns a conflict. Extend canonical turn replay validation to include the ordered recording identities alongside existing text and source-kind checks. A changed attachment list must not silently rewrite a previously accepted turn. Two intentional recordings remain distinct even if their bytes match; no cross-user content deduplication is required.
- **Transcript provenance:** keep the accepted text as the canonical narrator source, with the original ASR result attributable to its recording. Preserve recording references when the storyteller edits the transcript or mixes typed additions with dictated text. Later corrections use the existing versioning and invalidation rules and retain provenance to the original recording. Recording-level provenance does not establish exact word/time alignment; do not invent timestamps or treat edited additions as verbatim audio evidence.
- **Web integration:** carry recording descriptors through both voice mode and dictation. Keep an ordered list when dictation appends several clips; do not overwrite earlier recording IDs. Include the list in the durable turn/retry snapshot and source-kind handling. Hold the references through transcript review, submission failures and uncertain receipts, and clear the draft only when acceptance is confirmed or the storyteller explicitly discards it. Retaking replaces the intended draft association without mutating a previous original.
- **Native integration:** extend the shared contracts/API client and existing recorder, encrypted transcript draft and turn outbox to retain the backend recording ID separately from the local clip ID. Editing the draft must not cause text-equality checks to lose recording provenance or downgrade it to typed-only input. A clip stored in the encrypted device vault is still local until the backend confirms persistence. Retain the existing foreground, duration, size, owner-switch and cancellation restrictions; no new background-transfer guarantee is introduced.
- **Identity and consent:** use verified Supabase principals, RLS and current consent/policy checks for all recording operations. Preserve associations through supported identity linking and guest transfer, and revoke the previous principal after an actual ownership transfer. Include new recording records in the same atomic ownership transition as their canonical sources; object access follows current ownership metadata rather than an obsolete path prefix. Capture permission is not retention, AI-processing or sharing consent. Preserve the product requirement for recoverable identity before retaining private recordings; current anonymous authentication alone does not establish that requirement.
- **Privacy lifecycle:** distinguish an unsubmitted uploaded draft from an attached recording. Cancelling before upload performs no backend write. Explicit discard after upload logically deletes the draft and schedules or retries exact-object cleanup; transcription alone never accepts a narrator turn or consumes a recall round. Source withdrawal, consent withdrawal or project/account deletion must fence subsequent audio reads and jobs under the existing policy mechanisms. Deleting only an audio asset must not silently delete accepted transcript text or rewrite its history. Physical cleanup failures retain an inaccessible tombstone and retry state, not a false claim of byte erasure.
- **Retention and operation:** retained originals follow the owning source/project retention policy. Do not introduce an arbitrary expiry or garbage collector that removes accepted or recoverable draft recordings as part of this feature. Persist draft status so later approved retention work can distinguish unsubmitted and attached assets. Log recording IDs, sizes, timings and safe failure codes; exclude base64, bytes, transcript content, credentials and storage access tokens from routine logs and model prompts. Storage acknowledgement and association are required source-ingestion work; optional workspace processing remains independent.
- **Compatibility:** retain the canonical API namespace and its existing compatibility adapter, text-only submissions, language behavior, payment/recall rules and prior history. Missing recording references in legacy transcript sources mean original audio is unavailable; `narrator_transcript` alone is not proof that audio exists. Upgraded microphone capture paths must always carry their saved recording references. Add incremental schema changes and Storage policies without rewriting existing source IDs, versions or turn identities.

## Testing Decisions

- **Confirmed primary seam:** the user selected the authenticated Memoir HTTP API boundary. Exercise audio submission, canonical turn acceptance, source/receipt/history reload and original-content retrieval as one behavior-focused workflow. Prefer the existing FastAPI application/TestClient and disposable PostgreSQL fixtures; do not introduce a new testing framework or make helper-call expectations the acceptance criterion.
- **What makes a good test:** prove what is externally observable: exact original bytes and checksum after retrieval, correct source association, durable readback, truthful stage/status responses, rejected unauthorized access and unchanged commercial usage. A successful transcription, a mocked storage method call or a page-local blob alone cannot satisfy preservation acceptance.
- **Existing prior art:** extend the speech integration and canonical-only conversation tests for API contracts; follow the private interview-photo acceptance pattern for authenticated HTTP through real SQL; follow private-photo PostgreSQL tests for RLS, immutable acceptance, deletion and ownership transfer. Existing guest conversation and canonical guest tests cover identity continuity. These are patterns to reuse, not evidence that audio retention already works.
- **Durable happy path:** submit a small valid recording, obtain its recording ID and transcript, edit the text, accept it as a narrator transcript, then retrieve source details, receipt/history and identical original bytes through a new application/storage client over the same persistent state. Verify the raw ASR text and submitted text remain distinguishable. Cover first, subsequent and resumed turns, plus supported source-acceptance execution modes.
- **Multiple clips and mixed input:** submit two clips, append their dictated text and a typed clarification, then accept one answer. Verify ordered, complete recording references after reload and unchanged bytes for both clips. Verify retaking or discarding one draft cannot replace another clip or an already accepted original.
- **Failure and retry behavior:** cover object upload failure, finalization failure, lost upload response, STT timeout/failure/empty text, interrupted association, rejected turn, lost turn response and reply failure after source acceptance. Verify saved originals remain recoverable, failed originals are never reported ready, repeated keys reuse identities, changed payload/key reuse conflicts, and retries neither duplicate narrator sources nor consume extra recall rounds. Verify changed recording lists on an accepted turn cannot silently succeed as a different submission.
- **Authorization and lifecycle:** use owner, outsider, anonymous-authenticated and transferred-account cases. Reject unowned, wrong-project, unfinished, withdrawn and deleted recordings before provider work or source acceptance. Verify direct object reads, listing, signing and overwriting cannot bypass policy. Verify account switching cannot consume stale recording results. Test explicit draft discard, audio-only deletion preserving text, source withdrawal and logical deletion followed by failed/retried byte cleanup.
- **Validation and compatibility:** use real small media fixtures for the formats emitted by supported web/native recorders, including WebM/Opus and MP4/M4A when supported by the configured decoder. Cover malformed base64, empty/corrupt/mislabeled media and exceeded encoded-byte/decoded-byte/duration limits. Verify English/Chinese metadata handling, typed answers, older transcript-only sources, absent legacy optional fields and API-client schema compatibility. Do not use arbitrary text bytes as proof of successful media validation.
- **Bounded client checks:** extend the existing browser voice-controls tests to verify recording reference propagation for automatic voice turns, dictation review, appended clips, cancellation and retries. Extend the existing native private-media and outbox tests for separate local/backend identities, edited drafts, queued retry and owner changes. These checks support the confirmed API seam; they do not replace it with a new full browser end-to-end requirement.
- **Evidence limits:** control STT and object-storage transport at their external boundaries for deterministic API tests, while using real SQL for persisted associations and native PostgreSQL roles for RLS. A single-user database fallback is not owner-isolation evidence. Separately verify actual private Storage HTTP behavior with bounded synthetic audio in an authorized development environment before claiming deployed retention. Real-device recording/format checks and real provider calls require their own observed evidence; this specification task runs neither.

## Out of Scope

- Implementing the feature, deploying migrations, changing production Storage policies or accessing customer recordings during this specification task.
- A new audio library, waveform editor, conversation playback UI, family sharing interface or audiobook experience. Authenticated backend retrieval needed to prove preservation is included.
- Storing Mira's generated speech as the storyteller's original, voice cloning, speaker identification, biometric inference or emotional analysis.
- Live transcription, direct WebRTC reinstatement, streaming audio protocols or a new resumable/background upload system. Do not claim those broader ingestion requirements are satisfied by bounded complete-recording uploads.
- Changing speech providers, transcription quality, model/voice selection, prices, entitlements, session rules or device recording limits.
- Precise word timestamps, diarization, automatic alignment of corrected text, or changing canonical evidence offsets.
- Recovering missing original audio from historical text, synthesizing replacement originals, backfilling old conversations or importing arbitrary external audio URLs.
- A new account-recovery provider, consent platform, retention policy, automatic draft expiry, general garbage collector or backup-erasure guarantee.

## Further Notes

This spec synthesizes the user's requirement and the working tree inspected on 16 October 2026 at baseline `a6c1c90`. The original requirement is preservation in backend storage in addition to text. No playback or sharing product was requested.

The earlier OpenAI STT and TTS spec already expressed original-audio retention as an intended outcome. The current connected transcription implementation returns text and metadata without saving audio, while the web flow supplies no recording ID and the native flow retains a local clip identity. This spec closes that concrete gap using the current canonical conversation architecture, rather than treating the older upload/session routes as proof of implementation.

The project glossary, full product specification, shared SaaS architecture, canonical memory/receipt contracts and native shared-backend ADR guide terminology and boundaries. Product requirements MED-01 and MED-04 support verified uploads and separation of originals from derivatives. Existing narrator source IDs, versions and evidence relationships remain authoritative for accepted text.

Product requirement ONB-02 requires recoverable identity before private-recording retention. The current authenticated anonymous journey and this requirement are not equivalent. Implementation must verify an approved recoverable identity/consent path before enabling retention for that journey; anonymous bearer authentication must not silently waive the requirement. Identity linking and transfer coverage describe preservation through the supported transition, not permission to bypass the retention prerequisite. Broader resumable ingestion and production native-media readiness also remain separate release obligations.

The user explicitly confirmed the authenticated API test boundary on 16 October 2026. The existing publication target is the `bohui/copyme2.ai` GitHub issue tracker with the verified `ready-for-agent` label. This task covers the specification and its publication; it does not implement the feature or change production services.
