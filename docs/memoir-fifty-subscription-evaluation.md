# Explicit original five-case 50-round subscription evaluation

This is a separate opt-in `subscription_fifty` profile on the existing owned
subscription session and native bootstrap. The default remains the two-case
15-round `subscription_progressive` profile with its original 160-request,
30-minute ceiling. Historical five-turn live guards, ten-round proofs, strict
budget adapters and all previous source proofs retain their own meaning.

## Approved bounds and original inputs

The campaign uses exactly the original ordered `memoir-five-case/1` inputs:

1. harbour-copper-notebook (en-AU)
2. chengdu-tea-ledger (zh-CN)
3. perth-workshop-compass (en-AU)
4. kunming-garden-lanterns (zh-CN)
5. sydney-platform-letters (en-AU)

Each case has its original 50 distinct narrator inputs. No 15-round dataset is
extended or repeated. Input bytes are pinned to SHA-256
`e7f705bc4a96537b01cb5cde7d412972bdd929de49d339bc6b1a95bc9cb43927`.
Hidden truth, expected answers and judge prompts are never added to runtime
inputs. Run-derived UUID5 owners/projects are fresh for each run and differ from
the historical profile's namespace; dataset fixture project IDs are not used.

Required explicit ceilings are no more than 600 client HTTP requests and 7,200
seconds per case, and 3,000 requests and 36,000 seconds globally. Smaller explicit
ceilings are allowed. Cases run sequentially in original order. One shared gate
reserves every client HTTP attempt before contact, including repeated metadata,
continuations, failures and refused HTTP responses. Reservations are not
refunded. Cases cannot be restarted, reordered or given a new budget in the
same campaign. Global time starts at reservation creation, including native
setup. Case time starts at its first original turn and covers all turn work,
workflow settlement, readback and final structural observation. Its original
absolute deadline never resets per turn or request. Expiry closes admission and
starts owned cancellation/cleanup; an uncancellable database/provider operation
may settle after the deadline, and receipts retain that elapsed-time uncertainty.

These are client-request and elapsed-time bounds. Gateway-internal retries,
actual provider requests, tokens, dollars and subscription headroom are not
proven. Closing a request cannot prove already-running upstream work stopped.
Receipts explicitly preserve that uncertainty.

## Saved evidence and entitlement boundary

The runner requires original-source extraction and a ready saved draft at every
checkpoint 5, 10, 15, 20, 25, 30, 35, 40, 45 and 50. It retains source mappings,
actual saved checkpoint readbacks, source-span references, section fingerprints
and revision consistency. Missing, failed or pending checkpoint state stops the
campaign. Partial evidence remains available, but every experiment output is
null after a failure, deadline, cancellation or cleanup failure.

The normal product's 20-free-round cap is unchanged. Only the task-owned,
owner-scoped synthetic `PostgresRest` HTTP facade returns a synthetic paid-status
Family entitlement with a task-local synthetic price identifier. This is neither a
purchase nor a real customer subscription. No payment table or payment provider
is changed. All five storages must match the fresh case owners and exactly this
synthetic entitlement before a listener or worker starts. Family extraction is
enabled within the existing collector/workspace paths (English from round 1;
Chinese from round 16, preserving the original scenario). Every focused recovery
request shares the same counted gate. Photo/judge/telemetry availability is
reported separately and is never inferred from a completed draft.

This profile establishes progressive original-turn/saved-draft evidence. It does
not claim all original five-case quality dimensions, family/photo paths,
chapter-wide word limits, event entailment, native production RLS, provider
cohorts or human semantic acceptance passed.

owned disposable PostgreSQL container, pinned existing executables, exact route,

Keep the plan, native receipt, content-free reservation journal, saved drafts
and cleanup evidence. A stopped/closed case is reported incomplete with its
original deadlines and counters. Any native cleanup failure invalidates all

## Optional bounded public photo research

The full campaign may explicitly add `--enable-public-photo-research` together
with `--photo-python-binary` and `--photo-python-sha256` for an already installed
Python environment. No installation is attempted. Missing dependencies are a
recorded unavailable capability, not an alternate provider or fabricated pass.

Research uses the application's existing Commons and Library of Congress
catalogue paths with a disposable `PhotoPages(repository=None)`. Only visible
current narration and accepted grounded places select a query. Positive English
and Chinese requests keep current-day/historical distinctions; private,
ambiguous and no-search turns produce explicit no-call receipts. The private
HTTP facade never writes real Supabase photo storage or subscriptions.

Every selected public HTTP attempt, including robots requests, redirects,
repeated attempts and image reads, reserves a durable content-free journal entry
before send. The separate public-HTTPS limits are 128 attempts per logical search,
256 per case and 1,280 globally; logical searches are also capped at two per case
and ten globally. These public catalogue requests are distinct from the 600/3,000
model-gateway request allowance. Only fixed public catalogue/image hosts and
TLS-verifying public-IP-pinned reads are admitted. Missing or truncated accounting
is unavailable, never silently zero. Completed responses and upstream cancellation
are not claimed from reservation counts.

The Google/Flickr browser, keyed search and LLM-assisted photo paths are refused
because they do not share this reviewed HTTP boundary. All searches run in owned
killable process groups within the original case/global deadline and a 180-second
per-search ceiling. Cancellation joins their processes and retains reservations;
cleanup/accounting failure invalidates the campaign. Python is rehashed before
launch, installed package versions are recorded, and receipts do not claim all
third-party package contents are pinned.

Photo service success is not browser UI acceptance. The separate browser receipt
validator requires matching scope and retained screenshot hashes, but cannot by
itself prove a browser executed. Real UI execution/network receipts and screenshots
remain required before claiming the browser portion of end-to-end coverage.

## Optional isolated real browser path

`--enable-browser-readback --browser-config /absolute/owned-config.json` adds the
reviewed native browser producer. The config is data only, limited to 2 MiB, and
must match `memoir-fifty-browser-config/1`. It identifies the exact source revision
and source root, a fresh output root inside this run directory, existing resolved
Node/Python/Chromium executables, installed `node_modules`, the existing Playwright
JavaScript entry, Next CLI and its installed CLI documentation. It includes SHA-256
pins for each executable/entry/document and every Git-tracked `apps/web` file. The
producer validates the full inventory, not a caller-selected subset. Python must
be the current native interpreter. Existing Python Playwright distributions may
already include their JavaScript driver entry; verify the actual installed path
rather than installing another package or guessing it.

Set `allow_browser_turns: true` in that config for original input submission
through the actual UI form. The runner then does not submit that round directly.
A separately mounted production `/turn` handler accepts only one armed original
case/round/project/language, a fresh client-turn UUID, and the exact current
product-owned UI text wrapper. The original `conversation_text` is unchanged.
Trusted correlation is injected only at this owned boundary before the same
counted runtime. Duplicate, replayed, altered, greeting and photo-upload turns
are rejected. Provider diagnostics/private reasoning do not enter the browser
response or screenshots. Only the disposable synthetic owner's storage client
can write during this armed turn; it closes independently of the runner's client.

The fixture mounts real production read handlers for canonical project restore,
history, source evidence, family, place, events, readiness and saved drafts.
Project restore writes only an owned in-memory adapter from existing canonical
rows. Browser-turn mode pre-provisions empty canonical project metadata in the
new disposable database, with zero sources/events/rounds. No replies, narration,
drafts or events are seeded. Revision-zero legacy draft imports and hidden
locale-backfill writes are rejected; the synthetic profiles use the production
initialized explicit-locale record.

A private verified frontend copy runs against this owned loopback API. Shared
frontend/service configuration is untouched. Each case owns its Node and Chromium
process groups, and each UI operation has a fresh context. Only exact scoped API
reads and its single armed form POST are permitted; synthetic authorization is
attached only to that loopback API path. Service workers, unapproved sockets,
subframes, popups, downloads and redirects are blocked. Optional visualization
libraries use exact versioned public URLs. Request counts are bounded per
operation (16–512), and startup probes are separately capped. No missing runtime,
package, browser or CLI documentation is automatically installed/downloaded.

The producer saves actual DOM/network/page-error observations and PNGs from every
original form turn and final case views, including available life-stage tabs.
Missing views and blocked enrichment stay visible. It verifies the final original
narration and actual retained model reply appear in the UI, and preserves partial
receipts on failure. All work and cleanup share the original case/global deadline;
unverified process-group cleanup is fatal. Readback-only mode remains available
with `allow_browser_turns: false`, but never claims the original turns were
browser-submitted.

Browser, API, model and public-photo receipts remain separate evidence. The
current semantic judge is not run, and the legacy formal-composition/timeline
marker expectations are not relabelled as equivalent to current canonical event
and private-checkpoint contracts. No source-only/offline test result proves the
native browser campaign happened or all seven skill acceptance dimensions passed.
